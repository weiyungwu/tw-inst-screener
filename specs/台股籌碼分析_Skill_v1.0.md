# 台股籌碼分析（TW Chip Analysis）Skill v1.0

## 1. Skill 名稱
台股籌碼分析

## 2. 目的
透過 tw-inst-screener 網站的 API，查詢台股「法人同步買超」與「主力吸籌掃描」的最新資料，整理成清單或單檔籌碼分析。所有數字都必須來自 API 回應，不可自行估算、補值或憑記憶回答。

---

## 3. 執行觸發
當使用者輸入：
- `法人同步買超`、`同步買超`、`外資投信都買的股票`
- `吸籌掃描`、`主力吸籌`、`今天吸籌清單`
- `查 2330 籌碼`、`分析 3481`、`XXXX 的籌碼怎麼樣`（XXXX 為 4 位數股票代號）
- `台股籌碼報告`
- 或明確要求依照本 Skill 查詢台股法人、籌碼、吸籌資料

即執行本 Skill。

---

## 4. 資料來源

### BASE 網址
`BASE = https://tw-inst-screener.<子網域>.workers.dev`

> 安裝本 Skill 時，請把 `<子網域>` 換成實際的 Cloudflare Workers 子網域。

### 端點
全部是 `GET`，回傳 JSON，不需要登入（除非網站設定了 API_TOKEN，此時要帶 `Authorization: Bearer <token>`）。

| 用途 | 網址 |
|---|---|
| A. 法人同步買超清單 | `{BASE}/api/cobuy?days=10&streak=5&insts=foreign,dealer&market=TPEX&sort=foreign&limit=50` |
| B. 吸籌掃描清單 | `{BASE}/api/scan?stage=ACCUMULATION,WATCH&min_score=50&market=TPEX&limit=50` |
| C. 單檔明細 | `{BASE}/api/stock/{4 位數代號}` |

### 資料更新時間
每個交易日台北時間 18:00 與 20:00 更新。盤中查詢拿到的是前一個交易日的資料，回答時必須說明資料日期。

---

## 5. 任務判斷與呼叫方式

### 任務 A：法人同步買超清單
使用者想找「某些法人同時買超」的股票時，呼叫 `/api/cobuy`。

| 使用者說法 | 參數 |
|---|---|
| 外資 | `insts=foreign` |
| 投信 | `insts=trust` |
| 自營商 | `insts=dealer` |
| 外資和投信都買 | `insts=foreign,trust` |
| 三大法人都買 | `insts=foreign,trust,dealer` |
| 沒指定法人 | 不帶 `insts`（預設外資＋自營商），並在回答中說明採用預設值 |
| 最近 N 天累計買超 | `days=N`（最多 10） |
| 連續買超 K 天 | `streak=K`（最多 10） |
| 上市／上櫃 | `market=TWSE`／`market=TPEX` |
| 前 N 檔 | `limit=N` |
| 依投信買超排序 | `sort=trust` |

篩選定義（回答時可引用）：勾選的**每個**法人都要各自符合「最近 `days` 日買賣超加總 > 0」且「從最後一天往前連續買超至少 `streak` 天」。

### 任務 B：吸籌掃描清單
使用者想看「主力吸籌、吸籌清單、分數高的股票」時，呼叫 `/api/scan`。

| 使用者說法 | 參數 |
|---|---|
| 吸籌、主力吸籌 | `stage=ACCUMULATION` |
| 觀察名單 | `stage=WATCH` |
| 過熱、漲多 | `stage=OVERHEATED` |
| 吸籌加觀察 | `stage=ACCUMULATION,WATCH` |
| 分數 X 分以上 | `min_score=X` |

### 任務 C：單檔籌碼分析
使用者指定股票代號時，呼叫 `/api/stock/{代號}`。

- 使用者只給名稱（例如「台積電」）時，先確認代號；無法確定就請使用者提供 4 位數代號，不要猜。
- 只支援 4 位數普通股代號。ETF（例如 0050）、權證、債券不支援。

### 任務 D：交叉比對
使用者要「兩份清單都有的股票」或「台股籌碼報告」時：
1. 呼叫 `/api/cobuy`（依使用者條件）。
2. 呼叫 `/api/scan?stage=ACCUMULATION,WATCH&limit=200`。
3. 取代號交集。
4. 對交集中的個股（最多 5 檔）逐一呼叫 `/api/stock/{代號}` 取得明細。

## 6. 欄位與單位（必讀，最容易出錯）

### `/api/cobuy`
- `*_sum`、`*_daily` 的單位是**張**（1 張 = 1,000 股），正數是買超、負數是賣超。
- `*_daily` 和 `trading_days` 一一對應，由舊到新，最後一個是最近的交易日。
- `*_streak` 是從最近一天往前連續買超的天數。
- `count` 是符合的總檔數，`stocks` 最多只回 `limit` 檔。

### `/api/scan`、`/api/stock`
| 欄位 | 單位 | 意義 |
|---|---|---|
| `score` | 分（0～100） | 總分 |
| `stage` | — | ACCUMULATION 吸籌（≥ 60）、WATCH 觀察（45～59）、OVERHEATED 過熱、NEUTRAL 中性、EXCLUDED 排除（成交值不足或資料不足） |
| `breakdown.inst` | 分（滿分 30） | 法人緩買 |
| `breakdown.concentration` | 分（滿分 30） | 籌碼集中 |
| `breakdown.price` | 分（滿分 20） | 價格未動 |
| `breakdown.volume` | 分（滿分 10） | 量能溫和 |
| `breakdown.margin` | 分（滿分 10） | 融資退場 |
| `inst_net_20_pct`、`trust_net_20_pct` | **% 股本**（0.8 = 0.8%） | 20 日外資＋投信／投信淨買超占發行股數 |
| `inst_buy_days_20` | 天 | 20 日中法人淨買超的天數 |
| `foreign_ratio_chg_20` | 百分點 | 外資持股比率 20 日變化 |
| `ret_20`、`dist_ma60`、`range_20`、`margin_chg_20`、`holders_chg_4w_pct` | **小數**（0.05 = 5%） | 20 日漲幅、季線乖離、20 日振幅、融資 20 日變化、股東人數 4 週變化 |
| `vol_ratio` | 倍 | 20 日均量 ÷ 60 日均量 |
| `avg_value_20` | 元 | 20 日平均成交金額 |
| `big400_pct`、`big1000_pct`、`retail_pct` | % | 400 張以上大戶、千張大戶、50 張以下散戶持股比例 |
| `big400_up_weeks` | 週 | 大戶比例連續週增 |
| `holders` | 人 | 股東人數 |
| `series[].inst_net` | **股**（不是張） | 每日外資＋投信淨買超 |

### 訊號標籤（signals）中文對照
`inst_steady_buy` 法人緩買、`trust_buying` 投信買超、`big_holder_rising` 大戶連增、`holders_declining` 股東減少、`price_quiet` 價格未動、`box_compression` 箱型收斂、`volume_mild` 量能溫和、`margin_exit` 融資退場、`overheated` 過熱、`tdcc_warming_up` 集保資料累積中、`missing:<欄位>` 該欄位資料不足。

### 缺值
欄位為 `null` 代表資料不足（停牌、新上市、不能融資、集保週數不夠）。**一律寫「資料不足」，不可當成 0，也不可推論方向。**

## 7. 分析規則

1. **先說資料日期**：`/api/cobuy` 用 `trading_days` 最後一天；`/api/scan`、`/api/stock` 用 `scan_date`。
2. **引用具體數字**：例如「法人 20 日買超 0.82% 股本、20 天中 13 天買超」，不要只說「法人買很多」。
3. **事實與解讀分開**：
   - 「籌碼數據」只寫 API 給的數字。
   - 「解讀」才做分析，使用「可能」、「顯示」、「需留意」等措辭。
4. **正反並陳**：同時指出支持吸籌的訊號，以及缺漏或不利的訊號（例如融資增加、漲幅已大、量能放大）。
5. **品質提醒**：`quality` 為 `tdcc_warming_up` 時，必須提醒「集保資料累積不足，籌碼集中分數僅供參考」。
6. **不給投資建議**：不說「可以買」、「建議進場」、「目標價」。

## 9. 例外處理

### 情況 A：API 無法連線
例如逾時、DNS 失敗、HTTP 5xx。必須說明：
> 本次查詢未能完成：無法連線到台股籌碼資料服務（錯誤：……），因此無法提供資料。

**禁止**改用記憶中的數字或其他網站資料替代。

### 情況 B：資料尚未產生
`/api/scan` 回 `503 { "error": "scan_not_ready" }`，或 `/api/cobuy` 回 `503 { "error": "data_not_ready" }`：
> 資料服務目前尚未產生今日資料（通常在交易日 18:00 後更新），請稍後再查詢。

### 情況 C：查無個股
`/api/stock` 回 `404 { "error": "not_found" }`：
> 查無 XXXX 的資料。本服務只涵蓋上市櫃 4 位數普通股（不含 ETF、權證），也可能是代號有誤或已下市。

### 情況 D：參數錯誤
回 `400`，回應會帶 `allowed`（允許值）或 `hint`（格式說明，例如天數必須是正整數）。依此修正參數後重試一次；仍失敗就向使用者說明。

### 情況 E：查詢成功但沒有符合的股票
`count` 為 0 時，只輸出：
> **目前沒有符合條件的股票**

並附上本次採用的篩選條件，建議放寬哪個條件（例如減少連買天數、少選一個法人）。**不可**自行放寬條件後當成原條件的結果回報。

## 10. 品質控制 Checklist

輸出前逐項確認：

- [ ] 是否所有數字都來自本次 API 回應？
- [ ] 是否寫出資料日期？
- [ ] `/api/cobuy` 的單位是否寫「張」？
- [ ] `series.inst_net` 是否當成「股」而不是「張」？
- [ ] 小數欄位（ret_20 等）是否正確換算成百分比？
- [ ] `% 股本` 欄位是否沒有再乘 100？
- [ ] `null` 是否寫成「資料不足」而不是 0？
- [ ] `quality` 為 `tdcc_warming_up` 時是否有提醒？
- [ ] 是否說明了採用的篩選條件（含預設值）？
- [ ] 事實與解讀是否分開？
- [ ] 是否沒有任何買賣建議或目標價？
- [ ] 結尾是否註明「僅供研究參考，非投資建議」？
- [ ] 查詢失敗時是否說明原因，而不是編造資料？

## 11. 核心原則

> **資料只來自 API。**

不使用記憶、其他網站或推測的數字；API 沒給的就說沒有。

> **單位比結論重要。**

張與股、% 與小數、百分點與百分比，任何一個搞錯，整份分析都是錯的。

> **缺值就是缺值。**

`null` 代表不知道，不代表 0，也不代表沒有變化。

> **事實與解讀分離。**

數據段落只寫數字；解讀段落才分析，並標示不確定性。

> **不給投資建議。**

本工具是籌碼與價量的統計篩選，分數權重是 v1 主觀設定，尚未經回測驗證。
